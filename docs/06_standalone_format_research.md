# 외부 파서 없이 SDOCX 구조 조사

연구일: 2026-10-14 · 실행 환경: WSL / 시스템 Python · 대상: 기존 세 SDOCX

## 1. 결론과 범위

**Python 표준 라이브러리만으로 세 샘플의 페이지/객체 구조와 2,322획·377,690점의 필기를 복원했다.** 새 분석기는 ZIP과 압축 해제 폴더를 같은 구조로 읽는다. Dietrich 등의 설치·import·실행과 기존 모델 JSON에 의존하지 않는다.

사용자 지시에 따라 Windows 백업은 일단 압축 해제된 SDOCX와 같은 노트 묶음이라고 가정한다. 실제 sdoc/wdoc/SQLite 폴더에서 이 가정이 맞는지 확인하는 일은 Windows 연결 단계로 미룬다. 이번 핵심은 바이너리 형식과 자체 해독 코드다.

이 결과는 최종 PDF 변환 완료를 뜻하지 않는다. PDF 원본은 바이트 그대로 회수했고 배경 페이지 연결을 해독했으나, 텍스트를 보존하는 PDF 합성 엔진은 아직 없다. 필기 좌표와 압력을 알아도 삼성 펜의 동적 굵기/재질을 정확하게 재현하려면 추가 연구가 필요하다.

## 2. 실행물과 결과 계약

- 코드: [inspect_sdocx.py](../research/standalone/inspect_sdocx.py)
- 실행법: [standalone README](../research/standalone/README.md)
- 근거: [PROVENANCE](../research/standalone/PROVENANCE.md)
- 최종 실행 결과: `research/output/standalone-2026-10-14/` 아래 `jssc`, `msd`, `pss`, `msd-folder`.
- 초기 시행 결과 `standalone-msd`, `standalone-msd-v2`, `standalone-jssc`, `standalone-pss`, `standalone-msd-folder`도 보존했다. 첫 `standalone-msd`는 미디어 버전 차이로 중단한 부분 결과다.

각 실행은 `raw/`, `structure.json`, `summary.json`을 만든다. 후속 코드는 `pages → layers → objects → subrecords → stroke`에서 좌표/압력 등을 읽고, `pages → properties → pdf`에서 원본 자산 경로·페이지 번호·노트상의 사각형을 얻을 수 있다. `raw/`와 레코드의 offset/length를 함께 보관하므로 미해석 필드를 다시 연구할 때 외부 모델을 재생성할 필요가 없다.

전체 페이지를 보존하며 끝의 빈 페이지를 임의 제거하지 않는다. 도형과 이미지도 프레임과 원본 범위를 남긴다. 모든 실행의 `render_ready`는 `false`다.

여기서 PDF 배경 수는 `.page`에서 읽은 참조 수다. PDF 자체의 페이지 트리나 텍스트를 새 코드가 파싱해서 얻은 수가 아니다. 기존 연구의 PDF 텍스트/회전 관측은 [이전 기록](05_structure_research.md)을 따른다.

- 페이지 버전은 모두 4000이다.
- 실제 `mediaInfo.dat` 버전은 5500이다. 참고 문서의 5304와 다르지만, 관측한 5500의 엔트리는 같은 필드 순서와 길이 경계로 읽혔다. 다른 버전까지 일반화하지 않는다.
- 페이지 속성 영역과 레이어 영역의 미소비 바이트는 세 샘플 모두 없었다.
- 필기는 압축 형식이고, 관측한 geometry tail은 `0200`이다. 이 값의 의미는 미확정이다.
- 노트 ID는 세 샘플 모두 빈 문자열이다. 입력 폴더명을 실제 노트 UUID로 대신 기록하지 않는다.
- MSD ZIP/폴더 실행의 `structure.json`은 바이트 단위로 동일했다. 이것은 압축 해제 폴더의 등가성이지 실제 Windows 백업 구조 검증이 아니다.

## 4. 형식을 이용하는 순서

### 컨테이너와 연결 관계

1. `pageIdInfo.dat`: 32바이트 검사값 → u16 페이지 수 → UTF-16LE ID와 32바이트 검사값 반복. 파일 이름 정렬 대신 여기의 순서를 사용한다.
2. `media/mediaInfo.dat`: u32 버전 → u16 엔트리 수 → u32 길이와 엔트리 → `EOFX`. bind ID를 파일명으로 연결한다.
3. `.page`: 처음 두 u32가 레이어/속성 절대 오프셋이다. 0x0E의 속성 마스크를 읽고 0x12부터 크기/방향/ID/버전을 읽는다.
4. PDF 배경은 속성 비트 `0x100`에 있으며 파일 ID, 0 기반 페이지 번호, 사각형이 한 항목이다. 버전 4000에서 사각형은 float가 아닌 **int32 네 개**다.
5. 캐시 비트 `0x400`의 레코드는 원문 hex로 보존한다. PDF 참조 대신 캐시 파일을 최종 원본으로 삼지 않는다.

### 레이어와 객체

레이어 수/현재 레이어는 u16이다. 각 레이어의 header size로 object count 위치를 찾고 객체를 순서대로 읽는다. 객체는 `u8 type + u16 child_count + u32 size` 다음에 payload와 32바이트 검사값을 가진다. size는 검사값을 포함한다. 자식 레코드는 부모 뒤에 이어진다.

payload는 `u32 size + u16 type`의 하위 레코드들이다. 이 경계를 따라 읽어야 이미지나 도형의 바이트를 필기 좌표로 잘못 인식하지 않는다. 객체/하위 레코드 모두 원본 바이트 범위를 결과에 남긴다. type 7 도형 8개와 type 3 이미지 2개는 구조만 해독한 상태로 명시한다.

### 필기 좌표와 부가 배열

객체 type 1/15 내부의 하위 레코드 type 1에서 flexible offset, 마스크, 점 수를 얻는다. 현재 구현은 압축 형식을 지원한다.

- 첫 점: float64 x/y.
- 이후 점: 각 축의 u16 차분. 최상위 비트는 부호, 나머지 15비트는 절댓값이며 32로 나누어 이전 좌표에 더한다.
- 압력: 첫 float32 + 부호 있는 차분/128.
- 시간: 첫 int32 + unsigned u16 누적 증가량.
- 추가 축 비트가 있으면 기울기와 방향도 첫 float32 + 부호 있는 차분/32.
- flexible 영역의 알려진 선두 필드에서 advanced-setting ID, 직접 ARGB, pen size를 읽고 나머지를 hex로 보존한다.

색상이나 펜 이름이 간접 참조되는 경우를 완전히 해석하지 않았다. 압력과 pen size를 단순 곱한 선을 삼성노트와 동일한 렌더링이라고 간주하면 안 된다. 비압축 geometry는 미지원 오류로 남기고 원본 프레임은 유지한다.

### 노트 메타데이터

고정 헤더, 버전, 비어 있는 note ID, revision, 원시 시간값, 크기/패딩, 제목·본문 객체의 크기와 위치를 읽는다. 제목/본문 텍스트 자체와 뒤의 선택 속성은 아직 불투명 영역이다.

특히 관측한 `integrity_offset` 값은 제목/본문 뒤의 미해석 영역 초반을 가리킨다. 이를 근거 없이 모든 선택 속성의 끝이라고 해석하지 않는다. 기존 파서의 note.note 실패를 우회해 의미가 불확실한 필드를 정상 메타데이터로 기록하는 대신, 현재 코드가 확실히 읽은 범위를 구분한다.

## 5. 의존성과 출처

참고 자료의 형식 설명을 읽고 샘플 바이트에 맞춰 새 코드를 작성했다. 외부 구현을 복사하거나 GPL 파서를 묶지 않았고, `python3 -I -S`로 실행했다. 외부 저장소 체크아웃과 이전 가상환경을 제거하지는 않았지만 실행 경로에서는 사용하지 않는다. 출처·커밋·이전 코드 열람 이력은 PROVENANCE에 남겼다.

이번 범위의 “의존성 없음”은 **새 연구 도구의 추가 Python 패키지/외부 프로그램 의존성이 없음**을 뜻한다. 향후 PDF 합성까지 같은 원칙을 유지하려면 PDF 페이지 트리, 리소스/폰트, 압축 스트림, 회전/크롭, 참조 갱신을 다루는 자체 구현이 추가로 필요하다. 현재 결과만으로 그 단계가 해결됐다고 하지 않는다.

## 6. 다음 연구 순서

1. 도형 type 7의 geometry/스타일과 이미지 type 3의 자산 참조·크롭을 자체 해독한다. 실제 삼성노트 내보내기와 비교한다.
2. note.note 제목/본문·문자열 표·펜 설정의 실제 경계를 조사한다. 비공백 타이핑 텍스트가 있는 샘플이 필요하다.
3. 필기 렌더링을 별도 구현하고 압력/펜 설정의 영향과 겹침 순서를 비교한다.
4. 외부 라이브러리 없는 PDF 합성의 최소 지원 범위를 정한다. 원본 텍스트 보존이 필수이며 단순 래스터 PDF로 대체하지 않는다.
5. 단일 노트 변환이 성립한 뒤 Windows 실제 백업 연결, 등록, 감시, 안전한 PDF 교체를 붙인다.

현재 연구 도구는 전체 입력을 메모리에 읽으므로 매우 큰 노트의 메모리 사용 최적화는 남아 있다. 쓰기 중인 폴더의 일관된 스냅샷, 손상 파일 복구, 내장 해시 의미 검증, 실제 Windows 동작도 아직 지원·검증 범위가 아니다.

## 7. 첫 근사 복원 비교 — JSSC 노트 3페이지

2026-10-14에 자체 좌표 분석 결과의 5획·1,737점을 SVG로 그렸다. 저장된 ARGB와 pen size를 사용하고, 굵기 배율은 1.0, 선 끝과 꺾임은 round로 설정했다. 압력·속도·기울기는 굵기에 반영하지 않았다.

비교 자료는 `research/output/comparison-jssc-page003/`에 있다.

- `comparison-full.png`: 전체 페이지 좌우 비교.
- `comparison-detail.png`: 같은 노트 좌표 `(240,1180)-(920,1620)`의 확대 비교.
- `approximation.png`: 자체 복원 결과만 표시.
- `strokes.svg`: 표준 라이브러리만으로 생성한 필기 벡터.
- `comparison.json`: 비교 조건과 참고 이미지 경로.

왼쪽은 과거 Dietrich 연구 미리보기(thickness_scale=0.6), 오른쪽은 자체 필기 SVG를 원본 내장 PDF에 올린 결과다. 왼쪽은 삼성노트 화면 캡처나 삼성노트 직접 PDF 출력이 아니므로 원본 앱과의 일치 검증이라고 해석하지 않는다.

전체/확대 그림을 육안 확인한 결과, 이 페이지의 밑줄과 동그라미는 위치·색상이 유사하고 표시 내용을 읽을 수 있다. 자체 결과는 일정한 굵기로 더 균일하며 획 끝/두께 변화에 차이가 있다. 이 한 페이지의 성공을 모든 펜·형광펜·복잡한 필기 지원으로 일반화하지 않는다.

코드는 `research/standalone/render_strokes_svg.py`(의존성 없는 필기 SVG 생성)와 `research/make_page_comparison.py`(기존 PyMuPDF/Pillow를 사용하는 그림 제작)로 나눴다. 후자는 PDF/SVG를 화면 이미지로 만들기 위한 연구용 도구이며 외부 의존성 없는 최종 PDF 합성기가 완성됐다는 뜻은 아니다. 기존 Dietrich PNG를 읽을 뿐 외부 SDOCX 파서를 실행하지 않는다.

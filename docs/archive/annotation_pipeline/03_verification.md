# Samsung Notes → Obsidian 검증 계획

작성일: 2026-10-08 · 갱신일: 2026-10-13 · 상태: 샘플 3개 구조 추출 수행 / 정답 기반 품질 검증 대기

관련 문서: [개발 계획](01_plan.md) · [백로그](02_backlog.md)

## 1. 목적과 오류 우선순위

첫 관문은 자료에서 정확한 인용과 출처를 얻을 수 있는지 확인하는 것이다. 잘못된 문장이나 범위를 정상 인용으로 내보내는 오류를, 누락되어 수동 확인을 요구하는 오류보다 엄격히 막는다. 다음 관문은 사용자 글을 손상하지 않고 갱신하는지다.

이 문서는 검증 절차와 합격 기준이며, 구현 완료나 성능 보장을 뜻하지 않는다.

## 2. 샘플 준비

최소 50개 표시를 사람이 확인할 수 있는 대표 `.sdocx`를 확보한다. 한 노트에 몰아넣기보다 실제 자료의 언어·레이아웃·표시 방식이 드러나도록 구성한다. 최종 비율은 실제 사용자의 노트를 따른다.

필요 샘플:

- 텍스트 선택 하이라이트, 펜 밑줄, 펜 형광펜.
- 여러 줄 및 다단 PDF의 표시, 문장 일부 표시.
- 타이핑 메모, 손필기에서 변환한 텍스트, 미변환 손필기.
- 동그라미·화살표·괄호처럼 자동 인용 대상이 아닌 표시.
- 스캔 PDF와 정상 텍스트 PDF.
- 같은 PDF를 별도 삼성노트로 가져온 사례.
- 변경 전후 쌍: 표시 수정·삭제, 메모 추가, 노트 이름 변경·폴더 이동.

원본 화면 또는 사용자가 확인한 페이지 캡처를 정답 근거로 보관한다. 가능하면 가져오기 전 원본 PDF도 비교용으로 확보한다. 원본 PDF 별도 제공은 검증 보조 자료이며 정식 입력의 필수 조건으로 확정한 것은 아니다.

민감한 실제 자료는 공개 저장소에 올리지 않는다. 외부 AI API를 사용하지 않는다.

## 3. Gate 0 — 입력과 구조

| ID | 확인 내용 | 통과 조건 |
| --- | --- | --- |
| V01 | Windows 동기화 및 백업 | 태블릿 변경이 Windows 및 백업에 반영됨 |
| V02 | 원본 PDF 회수 | 추출 파일이 유효한 PDF이며 페이지가 누락되지 않음 |
| V03 | 원본 동일성 | 비교용 원본이 있으면 해시 비교. 다르면 차이 분석 후 ‘바이트 동일 원본’으로 주장하지 않음 |
| V04 | 페이지 연결 | 노트 페이지와 원본 PDF 페이지를 명시적으로 대응 가능 |
| V05 | 노트/페이지 ID | 반복 백업·이름 변경·수정에서 식별 결과 확인 |

PDF 회수·페이지 대응 등 핵심 전제가 실패하면 자동화 개발을 먼저 진행하지 않는다. 실패 원인, 영향 범위, 대안을 기록하고 범위를 다시 결정한다. README의 기능 설명은 통과 증거로 쓰지 않는다.

## 4. Gate 1 — 인용 추출 품질

### 4.1 정답 기록

표시별로 sample ID, 노트/페이지, 표시 유형, 기대 원문 범위, 실제 출력, 상태, 수정 필요 여부, 오류 원인을 기록한다. 줄바꿈·공백의 비의미적 정규화와 문장 경계 변경은 구별한다. 단어 누락·옆 단 혼입·다른 문장 선택은 정상으로 처리하지 않는다.

표시마다 한 행을 사용하고, [기록 양식](04_sample_annotations_template.csv)에 정답과 추출 결과를 함께 적는다. 실제 노트의 인용문과 파일 경로가 포함된 작성본은 공개 저장소에 넣지 않는다.

### 4.2 임시 합격선

대표 표시 최소 50개를 사람이 검토한다.

- 90% 이상은 문장 범위를 고치지 않고 자동 추출된다.
- 나머지는 확인 필요로 표시된다.
- 잘못된 인용을 정상으로 내보낸 사례가 있으면 원인을 수정하고 다시 검증한다.

이는 첫 개발 관문이며 전체 문서에 대한 90% 정확도 보장이 아니다. 잘못된 정상 인용이 테스트에서 0건이어도 모든 미래 입력에서 0건임을 뜻하지 않는다.

### 4.3 지표와 분모

| 지표 | 계산 또는 기록 |
| --- | --- |
| 자동 성공률 | 범위 수정 불필요하고 정상 처리된 표시 수 / 평가 대상 표시 수 |
| 수동 확인률 | 확인 필요 표시 수 / 평가 대상 표시 수 |
| 잘못된 정상 인용 | 잘못된 범위·원문인데 정상 처리된 건수 |
| 미검출 | 표시가 있는데 정상 결과와 확인 대기 모두에 나타나지 않은 건수 |
| 유형별 결과 | 선택형 하이라이트 / 펜 밑줄 / 펜 형광펜 각각 분리 |
| 실제 수동 부담 | 실제 자료 전체에서 수동 처리가 필요한 비율, 스캔·지원 외 유형도 별도 포함 |

미검출은 성공으로 간주하지 않는다. 인용 개수만 세어 실패 항목을 분모에서 제거하지 않는다. 처음 정한 샘플 구성을 결과를 본 뒤 유리하게 바꾸지 않는다.

펜 표시가 기준 미달이면 선택형 하이라이트만 자동화하고 펜 표시는 수동 확인으로 제한할 수 있다. 이때 지원 범위를 명시하고 선택형 표시의 합격선을 따로 검증한다. 기존 최소 50개 전체 결과도 그대로 남긴다. 필요하면 선택형 검증 샘플을 추가한다. 펜 표시가 주력이라면 이 제한 버전의 실사용 적합성은 별도 사용자 확인 전까지 미확정이다.

반복 수정에 사용한 샘플 외에 가능하면 미사용 샘플에서도 재확인하고, 추가 샘플 유무를 기록한다.

## 5. Gate 2 — 단일 노트 사용 흐름

| ID | 시나리오 | 기대 결과 |
| --- | --- | --- |
| U01 | 하나의 PDF 노트 import | Markdown 하나에 페이지별 인용·메모 집계 |
| U02 | PDF 페이지 링크 | 실제 Obsidian에서 올바른 원본 페이지 열림 |
| U03 | 미변환 필기 | OCR 없이 배경 포함 페이지 이미지 표시 |
| U04 | 메모 여러 개 | 원문과 개별 짝짓기 없이 해당 페이지에 모두 포함 |
| U05 | 수동 확인 입력 | 지정 영역에 붙여넣고 완료 표시 후 다음 실행에서 반영 |
| U06 | 관련 표시 변경 | 이전 수동 입력 보존, 재확인 요구 |
| U07 | 일부 페이지 확인 대기 | 기존 결과에 오래된 상태 표시, 다른 페이지 갱신 |
| U08 | 첫 import부터 확인 대기 | 출처·대기 상태가 보이고 정상 추출로 표시하지 않음 |
| U09 | 스캔/비지원 표시 | 지원 상태를 명시하고 조용히 누락하지 않음 |

링크 문법은 구현 후보가 아니라 실제 설치된 Obsidian에서 확인한다. 페이지 번호가 PDF 인쇄 쪽번호와 다른 경우 실제 파일 페이지 기준임을 표시한다.

## 6. Gate 3 — 식별·갱신·사용자 보호

| ID | 시나리오 | 기대 결과 |
| --- | --- | --- |
| S01 | 변경 없는 반복 실행 | 결과 파일/자산에 불필요한 변경 없음 |
| S02 | 수동 import 후 자동 발견 | UUID 확인 시 기존 Markdown 갱신, 중복 생성 안 함 |
| S03 | 같은 PDF의 다른 노트 UUID | 별도 Markdown 유지 |
| S04 | UUID 없음/중복 출력 UUID | 제목만으로 병합하지 않고 확인 요청 |
| S05 | Markdown 이름/위치 변경 | 사용자 경로 유지, 자산 링크 정상 |
| S06 | 소스 제목/폴더 변경 | 메타데이터 갱신, 사용자 출력 경로 강제 변경 안 함 |
| S07 | 개인 영역 작성 후 소스 갱신 | 사용자 텍스트 보존 |
| S08 | 자동 영역 직접 수정 | 기존 수정문 보존, 파일 갱신 중단 및 충돌 안내 |
| S09 | 마커 삭제/중복/불일치 | 추정 덮어쓰기 금지, 해당 파일 중단 |
| S10 | 반복 충돌 실행 | 안내가 중복 증식하지 않음 |
| S11 | 삼성노트 필기 삭제 | 자동 결과만 갱신, 개인 글과 페이지 구역 보존 |
| S12 | 원본 삭제/폴더 이탈 | 파일·자산 유지, 갱신 제외 표시 |
| S13 | 소스 일시 접근 실패 | 삭제로 잘못 처리하지 않음 |
| S14 | 페이지 추가/삭제/재배열 | 지원 외로 보류, 잘못된 출처 연결 금지 |
| S15 | 쓰기 직전 사용자 동시 수정 | 변경 감지 후 재처리/보류, 사용자 수정 덮어쓰기 금지 |

사용자 영역의 보호는 실행 전후 텍스트 비교로 확인한다. 단순 화면상 유사성만으로 판정하지 않는다. 충돌 해결 후 재개 과정도 한 번 수행한다.

## 7. Gate 4 — 백업·실패·자동 실행

- 변경 전 원본 버전이 보관되고 30일 정책이 적용되는지 확인한다. 테스트용 시각을 사용해 만료 경계를 확인한다.
- 최신 원본 및 삭제된 소스의 마지막 원본이 이력 정리로 사라지지 않는지 확인한다.
- 보관된 `.sdocx` 한 버전으로 재처리해 복구 가능성을 확인한다.
- 손상된 sdocx, 파싱 실패, 파일 잠금/쓰기 실패, 중간 종료를 대표 사례로 시험한다.
- 실패 시 원본·마지막 정상 Markdown·그 참조 자산이 유지되는지 확인한다.
- 출력 성공 전 성공 체크포인트를 기록하지 않는지 확인한다.
- 자동 실행과 수동 실행이 겹쳐도 동시에 같은 파일을 쓰지 않는지 확인한다.
- 30분 실행, 수동 바로가기, 일일 reconcile 기본안, PC 재가동 후 처리 흐름을 확인한다.
- 실행 결과 요약의 성공·확인 필요·충돌·실패 수가 실제 상태와 일치하는지 확인한다.

테스트는 정상·경계·현실적 실패를 중심으로 구성한다. 기능과 무관한 조합을 무제한 늘리지 않는다.

## 8. 성능과 실제 사용자 평가

최초 import와 변경 페이지 처리 각각의 시간, 페이지 이미지 크기, PDF 크기, 30일 원본 이력 용량을 기록한다. 아직 수치 목표는 합의하지 않았으므로 임의 SLA를 만들지 않는다.

실제 사용자에게 다음 작업을 맡긴다.

1. 지정 폴더 또는 파일을 가져온다.
2. 인용·메모·필기를 읽고 PDF 페이지를 연다.
3. 인용 확인 하나를 완료하고 개인 생각을 적는다.
4. 삼성노트에서 내용을 바꾸고 다시 동기화한다.
5. 개인 글 보존과 확인 상태 변화를 확인한다.

개발자가 아닌 사용자가 과도한 설명 없이 수행할 수 있는지, 수동 확인 비중을 받아들이는지 기록한다.
